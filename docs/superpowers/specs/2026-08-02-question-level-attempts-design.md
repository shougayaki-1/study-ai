## 1. 背景と問題

### 1.1 きっかけとなった課題認識

本人から次の3点が課題として挙げられた。

1. PDFの読み取りが浅くて、十分に分析できていない
2. その分析を長期間にわたって保存し、活用できていない
3. 分析内容を構造化し、最適な形でWebに反映できていない

### 1.2 調査で判明した実態

調査の結果、**1は事実誤認であり、真の原因は2にある**ことが分かった。

`vault/reports/daily/2026-08-01.md` を確認すると、夜間バッチのLLMは河合の解答履歴PDF
8件から、225問・117分・単元別正答率・設問番号（地理002・003・007…）・△（要確認）の区別
まで読み取れている。2026-07-31 のレポートでは431問を扱い、設問ごとの所要時間
（問題005に35分51秒）まで拾えている。**読み取り自体は十分に深い。**

問題はその出力先である。

| 観測事実 | 意味 |
| --- | --- |
| `_archive/` に29件の原本（模試PDF・写真）が存在する | 原本は保全されている |
| `subjects/` 配下は `英語L` と `英語R` の2科目のみ | 化学基礎・地理・公共・情報・古文・数学Cの誤答ログもカルテも存在しない |
| `runs/` の最終記録は 2026-07-26。一方 `reports/daily/` には 07-28・07-31・08-01 がある | 正規フロー（`start-run.mjs` → 誤答ログ → カルテ）を通らずレポートだけ生成された |

つまり「8月1日に225問解き、化学結合が弱く、地理の地図活用が8問中ほぼ全滅」という
最も価値のある情報が、**その日の散文レポート1枚にしか存在しない**。翌日以降、
人もAIも読み返さない。Webも同じレポートを表示するだけである。

3つの課題は独立ではなく、**「設問レベルの構造化データが存在しない」という単一の原因**に
帰着する。

### 1.3 実データによる裏付け（実装前に検証済み）

`pdftotext` と `pdftoppm`（poppler、macOS に導入済み）だけを使う約50行の検証スクリプトで、
`_archive/` の河合形式PDF 18件を解析した。既存の日次レポート（LLMが読んだ結果）との
突き合わせ結果は次のとおり。

| 科目 | 日次レポートの記述 | 決定的パーサの結果 | 判定 |
| --- | --- | --- | --- |
| 地理 | 19/27正解、誤答8問 | 27行 = 19○ / 8✕ | 一致 |
| 情報 | 9/12 | 12行 = 9○ / 3✕ | 一致 |
| 公共 | 9/16 | 16行 = 9○ / 7✕ | 一致 |
| 英語 | 3/7、4問誤答 | 7行 = 3○ / 4✕ | 一致 |
| 化学基礎 | 88問中 78正解 / 5誤答 / 6△ | 88行 = 77○ / 5✕ / 6△ | 合計一致・内訳が1問ずれ（78+5+6=89） |
| 2026-07-31 全体 | 431問 | 国語363 + 数学68 = 431 | 一致 |

**決定的パーサの方が正確だった。** さらにLLMは「88問中78正解」という要約しか残せないが、
パーサは88行すべてを単元・秒数付きで保持できる。

18件から **656試行 / ユニーク設問548 / 複数回解いた設問54** が復元でき、次のような
再演習履歴が取り出せた。

```
推量の助動詞|006   ○→✕→✕→✕→○→○
推量の助動詞|002   ✕→✕→○→○→○→○
補助動詞|009       ✕→○→✕     （65秒 → 8秒 → 15秒)
```

2026-07-31 の日次レポートはこれを「助動詞49/64」の一行に潰していた。
`補助動詞|009` が「一度できたのにまた落ちた＝定着していない」という事実は、
現在どこにも残っていない。

なお現時点で観測できた再演習はすべて同日内の解き直しである。日をまたいだ定着追跡は、
この形式で蓄積を開始して初めて可能になる。

### 1.4 ソース形式の多様性（設計上の最重要制約）

検証に使ったPDF（ファイル名 `tokuMo` 系）は**河合**のものであり、**東進のPDFは別形式**である。
さらに今後は手書きの丸付け写真を含む多様な形式が入る。

したがって本設計は「特定塾のパーサを書く」ものではなく、
**形式ごとのアダプタを追加していける器を作る**ものとする。河合形式アダプタは
「実証済みの1号機」という位置づけになる。

`_archive/` 29件の内訳は次の3種に割れた。

| 種別 | 件数 | 取り込み経路 |
| --- | --- | --- |
| 河合 tokuMo 形式（表形式・テキスト有） | 18 | 決定的アダプタ（検証済み） |
| 英検PDF（非表形式・テキスト有） | 4 | vision アダプタ（LLM） |
| 画像PDF（6ページ・3047×2150pt・テキスト0文字） | 3 | vision アダプタ（LLM） |
| ベクトル問題・回答（教材であり演習結果ではない） | 2 | 取り込み対象外 |

## 2. 目的と非目的

### 2.1 目的

- すべての取り込み経路が、同一スキーマの**設問レベル記録**を単一の追記専用ファイルに書く。
- 同じ原本を再取り込みしても二重計上しない。
- 同一設問の再演習を追跡し、「一度できたのに落ちた」を検出できる。
- Webが単元ごとの状態を、根拠（原本）まで辿れる形で表示する。
- 上記を、既存のvault・Markdown・夜間バッチ・Web画面を一切壊さずに実現する。

### 2.2 非目的

- Postgres canonical schema への移行（ロードマップ Phase 1）は本設計の範囲外。
  ただしフィールド名を揃え、将来の移行が単純なロードで済むようにする。
- 確率モデルによる mastery 推定は行わない。説明可能なルールベースに限る
  （親構想 `06-analysis-and-recommendations.md` 2.3「最初は説明可能なルールベースとする」）。
- 推薦・復習キューの生成は本設計の範囲外。本設計はその土台を作る。
- Webへの書き込み機能は追加しない。Webは完全read-onlyを維持する。

## 3. アーキテクチャ

```
vault/_inbox/<原本>
   │
 [1] 形式判定 (detect)         決定的。テキスト有無 / ページサイズ / ヘッダ語で fingerprint
   │     ├─ 既知形式  → 対応する adapter
   │     └─ 未知・画像のみ → vision adapter (LLM)
   │
 [2] adapter                   全adapterが同一スキーマの attempts[] を返す
   │     ├─ kawai-tokumo-history   決定的・実証済み
   │     ├─ vision-generic         LLM。手書き丸付け写真・英検・画像PDF
   │     └─ <東進 / 学校教材 …>     今後1本ずつ追加
   │
 [3] 正規化 (normalize)        科目名・単元をvault語彙へ寄せる。低確信は要確認TODOへ
   │
 [4] 追記                      vault/data/attempts.jsonl (append-only, 1設問1行)
   │                           + 原本を _archive/ へ移動（現行どおり）
   │
 [5] 派生物の再生成            単元別state → derived/*.json, subjects/*.md, reports/
   │
 [6] ミラー同期                現行 sync-vault-to-supabase.mjs + derived/*.json
```

### 3.1 境界の原則

- **adapter は「読む」だけを担い、蓄積・分析・表示は形式を一切知らない。**
  新しい塾・新しい画面・手書きノートが増えても、追加するのは adapter 1本だけであり、
  `/karte` も夜間分析も改修不要。
- **LLM経路も決定的経路も同じ JSONL に書く。** 手書き写真から読んだ誤答も、
  河合PDFから機械的に取った正誤も、同じ粒度・同じ場所に並ぶ。
  現状は前者が散文、後者が要約という分断が起きている。
- **決定的と vision は優劣ではなく適材適所。** 河合形式は決定的パーサの方が正確だったが、
  誤答タイプの判定は vision にしかできない。各行に `extractor.method` を残し、
  後から信頼度を区別できるようにする。
- **確信度の扱いは現行契約を踏襲。** 決定的アダプタは `confidence: 1.0`、
  vision は自己申告値。0.7未満は要確認TODOへ回す
  （[`2026-07-24-vault-conventions-contract.md`](./2026-07-24-vault-conventions-contract.md)）。

## 4. データ契約: `vault/data/attempts.jsonl`

1行 = 1設問への1回の取り組み。追記専用。

```jsonc
{
  "id": "a3f9c1e8b2d04a71",          // sha256(artifact_sha256 + page + row_index) 先頭16桁
  "schema_version": 1,

  "occurred_at": "2026-08-01T16:05:00+09:00",  // 時刻不明なら null
  "occurred_date": "2026-08-01",               // 時刻不明でも日付は必ず持つ
  "ingested_at": "2026-08-02T02:10:00+09:00",

  "source_system": "kawai",          // kawai / toshin / photo / eiken / school ...
  "artifact_ref": "_archive/2026/08/20260801-tokuMo-Chemics-1.pdf",
  "artifact_sha256": "9c1f…",
  "extractor": { "name": "kawai-tokumo-history", "version": "1.0.0", "method": "deterministic" },

  "subject": "化学基礎",              // vault語彙へ正規化済み
  "subject_raw": "化学基礎",          // 原本の表記をそのまま保持
  "topic_path": ["物質の構成", "化学結合", "分子とその形"],   // 大→小
  "topic_path_raw": "分子とその形 ＜ 化学結合 ＜ 物質の構成",
  "material": { "name": "河合 学習履歴 / 範囲選択", "question_no": "002" },

  "result": "correct",               // correct / incorrect / partial(△) / unknown
  "duration_sec": 25,                // 不明なら null
  "error_type": null,                // calc / knowledge / reading / logic / other / null

  "confidence": 1.0,
  "confirmation_status": "unreviewed",   // unreviewed / user_confirmed / user_rejected
  "record_status": "active",             // active / superseded / retracted
  "supersedes": null,
  "note": null
}
```

### 4.1 各設計判断の理由

**① `id` が原本ハッシュ由来 → 再取り込みしても二重にならない**

同じPDFを2回 Inbox に入れても同じ `id` になり、上書きされるだけ。
親構想 `06` の「同じPDFを再取り込みした結果を別証拠として数えない」を、
DBなしで満たす。現在のMarkdown追記方式にはこの保証がない。

**② 訂正は上書きせず `supersedes` 行を追記**

`_inbox/corrections.md` で「これは日本史ではなく世界史」と訂正したとき、元の行を消さず
`record_status: "superseded"` に変更し、新しい行を追記する。原本非破壊の原則を
構造化データ側にも通す。集計は `record_status === "active"` のみを見る。

**③ 決定的経路は `error_type` を絶対に埋めない**

河合PDFには問題文が含まれないため、計算ミスか知識不足かは**判別できない**。
ここをLLMに推測させると、もっともらしい誤りが長期データに混入する。
親構想の原則13「データがないと弱いを混同しない」の実装である。
`error_type` を埋めてよいのは、写真・記述答案からの vision 経路と、
対話での本人申告のみ。

**④ `topic_path` + `material.question_no` が同一性キー**

これが再演習追跡（`○→✕→✕→✕→○→○`）を可能にする。問題文を保存できなくても、
再演習の追跡と定着度の推定はできる。復習キューの土台がここで出来る。

**⑤ フィールド名を親構想 `02-canonical-data-model.md` と揃える**

`source_system` / `occurred_at` / `record_status` / `confirmation_status` /
`extractor` / `confidence` はすべて向こうの語彙である。この JSONL は
**「まだテーブルを作っていない Postgres」**であり、将来 Phase 1 へ進むときの移行は
単純なロードで済む。逆に Phase 1 へ永遠に進まなくても、単体で完結して動く。

### 4.2 ファイル配置

- `vault/data/attempts.jsonl` — 正本。ローカル（Mac）のみ。Supabaseへは同期しない。
- `vault/data/derived/skills-<科目>.json` — 派生物。Supabaseへ同期する。

## 5. 派生物とWeb

**原則: `attempts.jsonl` 以外はすべて削除して作り直せる。派生物にだけ存在する情報を作らない。**

### 5.1 派生物3種

**① `vault/data/derived/skills-<科目>.json`（新規）**

末端単元（`topic_path` の最下層）を1エントリとし、
`試行数 / 正答率 / 直近5回の結果列 / 最終演習日 / 平均秒 / state` を持つ、
Web専用の小さな事前集計。

**② `subjects/<科目>/誤答ログ.md` / `弱点カルテ.md`（既存・維持）**

役割のみ変わる。数値の集計部分は JSONL から決定的に生成し、LLM は解釈の地の文だけを書く。
これにより「88問中78正解/5誤答/6△」が合計89になるようなズレが構造的に消える。
既存の英語カルテのような質の高い散文分析はそのまま価値があるため維持する。

**③ `reports/daily/*.md`（既存・維持）**

同じく、集計は決定的・解釈はLLM。

### 5.2 Web: `/karte/<科目>` に弱点マップを追加

既存のカルテ本文はそのまま下に残し、上に単元マップを追加する（画面を作り直さない）。

```
化学基礎                                    最終演習 8/1

▼ 物質の構成 ＞ 化学結合
  電気陰性度と極性   ●●○●●   4/6   平均48秒   8/1    弱い
  分子とその形       ●●●●●   8/8   平均19秒   8/1    安定
  配位結合           ●●        2/2   平均41秒   8/1    データ不足
  分子間にはたらく力 ●○●○●   6/9   平均25秒   8/1    不安定
```

### 5.3 state 判定ルール

説明可能なルールベースのみ。確率モデルは導入しない。
判定は上から順に評価し、最初に一致したものを採用する。

| state | 条件 | 意図 |
| --- | --- | --- |
| **データ不足** | 試行数 < 3 | 弱いのか未着手なのかを区別する（原則13） |
| **弱い** | 直近5回の正答率 < 0.6 | 最優先の復習対象 |
| **不安定** | 直近5回で○✕の切替が2回以上 | `補助動詞\|009` の ✕→○→✕ を拾う。現状これが完全に見えていない |
| **安定** | 上記以外 | 触らなくてよい |

`partial`（△）は正答率計算上 0.5 として扱い、切替判定では `incorrect` 側とみなす。

### 5.4 ドリルダウン

単元をタップすると試行一覧（日時 / ○✕△ / 秒数 / 原本への参照）を表示する。
根拠まで1タップで辿れるため、「なぜ弱いと言われたか」を常に検証できる。

### 5.5 ミラー同期の扱い

現状 `analysis/helpers/sync-vault-to-supabase.mjs` は `.md` のみを同期し、
`src/lib/vault/vault-source-parity.test.ts` が fs / Supabase の等価性を守っている。

- `vault/data/derived/*.json` を同期対象に加える（小さい・画面専用）。
- `attempts.jsonl` 本体はローカルのみとする。18ファイルから656行が出た規模であり、
  1年で数万行・数MBになる。Vercelから毎回全件読むのは不適切。
  **重いものはMacに置き、Webには画面に必要な形だけ渡す** — 既存のクラウドミラー設計の思想に従う。
- 派生ファイルが存在しない科目は「まだ集計されていません」と表示する（エラーにしない）。

## 6. 移行と非破壊性

### 6.1 既存フローへの挿入位置

`analysis/nightly.md` の手順2〜6（Inbox解析 → 仕分け → 訂正反映 → カルテ差分 → レポート）は
そのまま残す。手順2の中に分岐を1つ追加する。

```
2. Inbox解析
   2-a. 形式判定 (detect)              ← 新規
   2-b. 既知形式 → 決定的adapter        ← 新規
        未知形式 → 従来のLLM読み取り     ← 現行そのまま
   2-c. attempts.jsonl へ追記           ← 新規
   2-d. 以降（仕分け・カルテ・レポート）は現行どおり
```

決定的アダプタが扱えないものは、現在と全く同じ挙動で処理される。

### 6.2 遡り取り込み（backfill）

`_archive/` の既存原本を遡って JSONL 化する。決定的経路は `id` が原本ハッシュ由来で
冪等なため、何度でもやり直せる。

対象内訳は 1.4 の表のとおり。河合形式18件を第一弾とする。

**既存の `subjects/英語*/誤答ログ.md` の過去記述は JSONL に取り込まない。**
設問粒度を持たない散文であり、無理に構造化すると捏造になる。二重計上も避ける。
英語カルテは散文のまま残す。これは「移行しない」という明示的な判断である。

### 6.3 feature flag と rollback

ロードマップの制約「各Phaseはfeature flagとrollbackを持つ」に従い、
環境変数 `STUDY_AI_ATTEMPTS=1` で有効化する。

**rollback は `vault/data/` を削除するだけで完了する。** 既存のMarkdownを一切変更しないため、
完全に元の状態に戻る。派生物にしか存在しない情報を作らない設計にした結果である。

### 6.4 前提として先に解消すべきこと

`runs/` が 2026-07-26 以降記録されていない件は、backfill の前に原因を特定する必要がある。
2026-07-28・07-31・08-01 のレポートは `start-run.mjs` を通らずに作られており、
ロック取得・訂正反映・カルテ更新をスキップした経路になっている。この状態のまま
新ステップを追加すると、「動いているつもりで動いていない」が二重になる。

## 7. テスト戦略

### 7.1 adapter を2層に分割する

```
kawai-tokumo-history.mjs
  ├─ extractRaw(file)    外部コマンド実行のみ (pdftotext / pdftoppm)。薄く保つ
  └─ parse(rawText, rawPixels) → attempts[]   純関数。ここに全ロジック
```

`parse` が純関数であるため、実PDFなしでテストできる。これは必須要件である。
`vault` は Google Drive 上のリポジトリ外にあり、さらに親構想 `08`（著作権・個人情報）から
**実PDFをリポジトリに置けない**。fixture は `pdftotext -bbox-layout` の出力と
正誤列の色サンプル値を、数値と単元名だけに匿名化したものとする。

### 7.2 テスト項目

| 種別 | 内容 |
| --- | --- |
| ゴールデン | fixture → 期待 attempts[]（行数・正誤・単元分解・秒数） |
| 突き合わせ | 地理19/27・情報9/12・公共9/16・英語3/7・2026-07-31が431問 |
| 冪等性 | 同じ原本を2回取り込んでも active 行数が変わらない |
| 訂正 | `supersedes` 追記後、集計から旧行が消え新行が入る |
| state判定 | 4状態それぞれの境界（試行2件=データ不足、3件目で判定開始 など） |
| 既存互換 | `vault-source-parity.test.ts` に derived JSON を追加。fs と Supabase で同じ結果 |

### 7.3 品質ゲート（黙って落とさない）

決定的アダプタは毎回 `unknown_marks`（色判定できなかった行数）を返す。
**1件でもあれば要確認TODOへ回す。** 検証した18件では0件だったが、
河合が配色を変更したら即座に気づける。パーサが静かに壊れて「全問正解」になる事故を防ぐ。

同様に、`detect` が既知形式と判定したのに抽出行が0件だった場合もエラー扱いとする
（フォーマット変更の検知）。

## 8. 依存関係の制約

## 9. 検証済みの技術的事実

実装者が再確認せずに前提としてよい事実を記す。

1. 河合 tokuMo PDF の正誤列は**テキストでも画像でもなくベクター描画**であり、
   `pdftotext` では取得できない。`pdffonts` に○✕△のグリフは存在せず、
   `pdfimages -list` にも該当画像はない。
2. 正誤は**色で判別できる**。○ = 緑（RGB およそ 68,176,47）、△ = 橙、✕ = 赤。
   `pdftoppm` で 150dpi の PPM を出し、正誤列の矩形内で彩度の高い画素の平均色を見る。
3. 行の座標は `pdftotext -bbox-layout` の `<word>` 要素から得られる。
   解答時間（`\d{2}:\d{2}:\d{2}`）の y 座標が行の基準として安定している。
   正誤列・科目列の x 範囲は、テーブルヘッダの「正誤」「科目」から得る。
   **ページ内で「最後に出現するもの」を使うこと。** 1ページ目には絞り込みフォームがあるため
   2回出るが、2ページ目以降とフォームの無い版面では1回しか出ない。
   「2つ目」を要求すると該当ページがまるごと0行になる。
4. 行間隔は約 23.7pt で規則的だが、**行間隔を仮定せず各行の実座標を使う**こと。
5. `区分` 列は `小単元 ＜ 中単元 ＜ 大単元` の順で並ぶ。`topic_path` へは**逆順**に格納する。
   なお `区分` セルは**1つの `<word>` ではなく、単元名と `＜` が別々の `<word>` に分割される**
   （例: `金属結合・金属結晶` / `＜` / `化学結合` / `＜` / `物質の構成` の5要素）。
   さらに `＜` は他の語より y 範囲が狭い（フォントサイズが異なる）。
   文字列を `＜` で split するのではなく、**x 順に並べた word 列から `＜` を除いて組み立てる**こと。
6. **セルは1行に収まらないと折り返し、1つの行が複数のサブ行になる**（数学のPDFが該当）。
   単元 `… ＜ 平面` + `ベクトル`、科目 `数学` + `C` のように語が分断されるため、
   帯の中を「y でサブ行にまとめ → サブ行を上から順 → 行内は x 順」に走査し、
   `＜` 区切りで各区間を連結する必要がある。x だけでソートすると壊れる。
7. **単元列と科目列の境界は、固定した x 座標では決められない。**
   数学は単元テキストが x=463 まで伸び、情報は科目テキストが x=408 から始まるため、
   全ファイル共通の境界線が存在しない。
   **科目ヘッダ中心の左60pt以内にある語のうち、直前の空白が最も広い位置**を境界とすると、
   18ファイルすべてが正しく分離できる（実測で確認済み）。
8. 1ページあたり最大50行。それを超えると次ページに続く。

## 10. 既知の限界（本設計では解決しない）

実データ18件の解析で判明した、意図的に先送りする事項を明示する。
「気づいていない」と「先送りした」を区別するために記録する。

### 10.1 `科目` 列に教材名が入ることがある

18件から抽出できた科目名は次のとおりで、粒度が揃っていない。

```
古文単語 / 古文文法 / 漢文 / 数学C / 化学基礎 / 地理総合 / 公共 /
高校英単語 / ベストフィット情報Ⅰ（実教出版）
```

`ベストフィット情報Ⅰ（実教出版）` は科目ではなく教材名である。
また `古文単語` と `古文文法` は教材の区分であり、科目としては同じ国語に属する。

本設計では **`subject` に原文をそのまま入れ、正規化を行わない**。
理由は、正規化辞書を先に決め打ちすると、実際に入ってくる表記の幅が分からないまま
誤った対応表を固定してしまうためである。まず生の表記を蓄積し、
実データが揃ってから対応表を作る。

影響として、`/karte` の科目一覧に教材名が混じる。表示上は不自然だが、
データは失われず、後から `subject` の正規化を派生物側で行えば解消できる。

### 10.2 誤答タイプが埋まらない

河合PDFには問題文が含まれないため、決定的経路では `error_type` が常に `null` になる。
誤答タイプは vision 経路（写真・記述答案）と本人申告からのみ埋まる。
これは仕様であり不具合ではない（4.1③参照）。

### 10.3 対応するのは河合形式のみ

東進のPDF、英検PDF、画像PDF、手書き写真は本設計の範囲では
従来どおり vision 経路が扱う。設問レベルの記録は残らない。
これらは後続のアダプタ追加で順次対応する。
