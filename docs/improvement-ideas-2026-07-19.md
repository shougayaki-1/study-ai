# study-ai 発展アイデア(2026-07-19)

このセッションでアプリ全体を触った上での、便利にするための発展案。
インパクト÷労力で並べている。共通テストまで約6ヶ月(2027-01-16)という時間軸を前提。

## 最優先: データ品質 — `unit_id` が埋まらない問題

**現状の実測**: `question_results` 263件中 **228件(87%)が unit_id=null**、
`study_sessions` 15件中 **14件が unit_id=null**。

弱点スコア・ヒートマップ・復習提案はすべて `unit_id` を軸に動くのに、
実データの大半で null。つまり分析エンジンの燃料がほぼ空。原因は2つ:

1. **共通テスト演習(common_test)の記録に単元選択欄が無い**
   ([record/page.tsx](../src/app/record/page.tsx))。年度/大問しか選べない。
2. **Notion取り込みデータ**は科目・大問までしか対応が取れず、意図的に unit_id を
   null にした(228件の多くはこれ)。

### 案1. 共通テスト演習に「大問→単元」の簡易マッピングを持たせる(効果特大 / 労力M)
共通テストは大問と出題分野がほぼ固定(例: 地理 第1問=地図・地理情報、
数学IA 第3問=場合の数と確率)。年度×大問→単元の対応表を1つ持てば、
common_test 記録でも自動で unit_id が付き、既存の分析が一気に生きる。
`supabase/schema.sql` に対応表テーブル、`record/page.tsx` で大問選択時に自動補完。

### 案2. Notion取り込みの unit_id 精度を上げる(効果中 / 労力M)
`import-notion-mock-exams.mjs` は地学基礎・現代文しか単元マッピングしていない。
案1の大問→単元対応表を共通化すれば、模試の設問ログ258件も単元別に効いてくる。

## 高レバレッジ

### 案3. 間違いノート(誤答ログ)ページ(効果特大 / 労力M)
`question_results` に `error_type`(calc/knowledge/reading/logic/other)が
既にあるのに、間違いだけを一覧・復習する画面が無い。
「未復習の誤答」を科目×誤答タイプで絞り込み、チェックで復習済みにできる画面を作る。
デジタル間違いノートは"書いて終わり"になりがちなので、
**復習提案(review_tasks)と連動**させ、未復習の誤答が自動で提案に乗る形にすると生きる。
既存の `question_results.corrected_at` / `needs_review` の仕組みを流用可能。

### 案4. `plan_blocks`(学習タイムテーブル)を朝Push・記録と連動(効果中 / 労力M)
`plan_blocks` テーブルと schedule/record UIは既にあるが、
`linked_session_batch_id`(計画と実績の突合)が活かしきれていない。
「計画した学習ブロックのうち何%を実行できたか」を stats に出すと、
計画倒れの可視化になり、翌日の現実的な提案時間の根拠にできる。

### 案5. 復習提案の「消化率」フィードバックループ(効果中 / 労力S)
毎晩3〜5件提案しているが、実行された割合が分析に還っていない。
`review_tasks.status`(completed/expired)は貯まっているので、
「提案の◯%が実行された/未実行の提案は翌日どう再評価するか」を
nightly.md の判断根拠に組み込むと、提案が現実的な量に自動調整される。

## 中〜長期

### 案6. FSRS風の単元別復習間隔(効果中 / 労力L)
現状の弱点スコア `(1-正答率)×(1+log(1+経過日数)/2)` は素朴な忘却近似。
単元ごとに「前回正誤→次の最適復習日」を持つFSRS風の軽量スケジューラにすると、
"いつ復習すべきか"が正答率の履歴から出る。カード単位のAnkiは要らず、
単元単位で十分。`unit_state_snapshots` に安定度パラメータを1列足す程度で始められる。

### 案7. 過去問ペース管理(効果中 / 労力M)
共通テスト直前期は「大問別の時間配分ドリル」が重要。
`study_sessions` に演習時間は入るが、大問ごとの目標時間との差(東進PDFにある
「目標時間」)を追う仕組みが無い。模試PDFの目標時間データを活かして
「時間内に解けているか」を可視化すると、暗記科目より配点効率の高い改善点が見える。

### 案8. 志望校判定の推移グラフ(効果中 / 労力S)
`mock_exams.judgments_json` に志望判定(A〜E/Z)が既に入っているのに、
stats では最新1件しか出していない。模試ごとの判定推移を第1〜6志望まで
折れ線/バッジで見せると、モチベーションと戦略判断(どの科目を伸ばすと
どの志望が上がるか)に直結する。

### 案9. 週次レポートに「科目別 費用対効果」を入れる(効果中 / 労力S)
`mock_exam_scores` に偏差値・平均点・順位が入っている。
「学習時間あたりの偏差値の伸び」を科目別に出すと、
時間の再配分判断(伸びしろの大きい科目に寄せる)ができる。
既存の daily-summary + mock_exam_scores の突合だけで実装可能。

## 運用・UXの細かい改善

### 案10. 重複アップロード検知(効果小 / 労力S)
今日、同一PDFが3回アップされていた(手動で重複排除した)。
`photos` にファイルのハッシュ列を足し、アップロード時/バッチ処理時に
既存と同一なら自動でスキップすれば、二重計上と手作業が減る。

### 案11. バッチ実行のワンボタン化(効果中 / 労力M)
夜間分析は手動で対話セッションを開いて nightly.md を流す運用。
`analysis/menubar-app`(既存のElectronメニューバーアプリ)から
「今すぐ分析」を押すだけで走るようにすると、実行忘れが減る。
サブスク制約で完全自動化は不可だが、起動の手間は下げられる。

### 案12. schema.sql の実DB自動適用(効果小だが地味に重要 / 労力S)
今日、schema.sql に定義済みだが実DBに未適用のカラムがあり、
バッチが落ちた。他セッションがスキーマを変えても、
バッチ起動時に `supabase db query --linked --file supabase/schema.sql` を
先頭で流すようにすれば(冪等なので安全)、この種の事故を防げる。
